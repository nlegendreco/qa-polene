## Règles de travail

- **Langue** : tout en français (échanges, noms d'étapes, messages d'erreur, docs). La personne avec qui on travaille est la QA du projet, pas un profil développeur : expliquer simplement, sans jargon inutile.
- **Commandes préprod** : chaque achat préprod crée une vraie commande de test (un lancement complet = 4 commandes). Ne jamais lancer de test préprod qui va jusqu'au paiement sans accord explicite. Pas de commande le soir.
- **Prod** : jamais de paiement. Les tests prod s'arrêtent à l'arrivée sur le checkout. On peut lancer `npm run test:prod` à tout moment.
- **Données personnelles** : aucune donnée réelle dans le dépôt. Le mot de passe préprod, l'email du client de test, les identifiants du compte de test de la prod et les infos de carte restent dans `.env` (non versionné). Ne jamais écrire l'email personnel de la QA dans un fichier versionné. Les dossiers `emails/`, `.auth/`, `archives/`, rapports et résultats sont exclus de Git.
- **Git** : commit et push uniquement sur demande. Vérifier `git status` et l'absence de secrets avant chaque commit.
- **Vérifier avant d'annoncer** : un changement de test est validé par un lancement réel (prod sans restriction, préprod avec accord). Dire clairement ce qui n'a pas été testé.
- **Suivi** : après chaque étape, mettre à jour la section « Suivi » ci-dessous et le tableau « Avancement » de la roadmap.

## Environnements

| | Prod FR | Préprod |
|---|---|---|
| URL de base des tests | `https://www.polene-paris.com/` | `https://asia-polene.myshopify.com/fr-fr/` |
| Accès | Public | Mot de passe Shopify (`PREPROD_PASSWORD`), saisi par `tests/auth.setup.ts` |
| Jusqu'où va le test | Arrivée au checkout | Confirmation de commande |
| Paiement | Aucun | Carte de test Shopify Payments 4242 4242 4242 4242 |

Préprod : par défaut en anglais / USD / marché US, d'où le préfixe `/fr-fr/` (non mémorisé, il faut le garder sur chaque URL). Même en `/fr-fr/`, une partie des textes du thème reste en anglais et les prix diffèrent de la prod. Un seul moyen de paiement (carte) et un seul mode de livraison.

Autres boutiques de prod (pas encore testées) : `uk-polene`, `jp-polene`… une boutique Shopify et un thème par marché.

## Commandes

```bash
npm run test:prod                       # prod, 4 appareils, sans commande
npm run test:preprod                    # préprod, 4 appareils = 4 commandes de test (+ contrôle des produits fixes)
npm run test:donnees                    # préprod : état des 9 produits fixes, Chrome seul, sans commande (à tout moment)
npm run donnees:qa                      # préprod : crée / remet en état les produits, collections et menu QA (data/donnees-qa.json), montre les changements puis attend « oui »
npm run donnees:qa -- --apercu          # même liste de changements, sans rien modifier
npm run connexion:compte                # préprod : la QA se connecte au compte +qacompte (code par email), session gardée dans .auth/compte-client.json
COMMANDE_COMPTE=1 npx playwright test compte-client --project "preprod · desktop-chrome" --grep "Commande d"   # 1 commande préprod du compte de test (accord QA)
npx playwright test --grep @pdp         # seulement les tests d'un type de page (voir « Étiquettes de page »)
npx playwright test --project "prod · iphone" --headed
npx playwright test --ui                # suivi visuel étape par étape
npm run rapport:polene                  # sommaire des dernières séries (une carte par série), servi en local
npm run rapport:polene -- visuel        # Rapport Polène d'une série (tnr, visuel, regressions, demo-echec)
npm run rapport:polene -- archives/2026-10-07-poc   # sommaire d'une archive (exécution de référence des POC)
npm run rapport                         # rapport Playwright d'origine de la série tnr (détail technique)
npm run test:demo-echec                 # échec volontaire (POC 1.6)
npm run test:visuel                     # POC 2 : 4 pages (accueil, fiche nouvelle et ancienne, panier) × 4 appareils comparées à references/ (prod)
npm run test:visuel:maj                 # sauvegarde references/ dans archives/references/<date>/, puis reprend la référence (accord QA)
npm run test:regressions                # POC 2.5 : 4 régressions injectées, les 8 tests doivent échouer
npm run test:accessibilite              # axe sur 51 pages (prod et préprod, Chrome ordinateur et iPhone) comparé aux relevés, + bouton pause / lecture au clavier, sans commande (à tout moment)
npm run test:accessibilite:maj          # enregistre les corrections dans references/accessibilite/ (le relevé ne fait que rétrécir ; accord QA)
npm run archiver -- <nom>               # copie les rapports de toutes les séries dans archives/<date>-<nom>/ (hors Git)
SERIE=essai npx playwright test …       # essai rangé dans resultats/essai/, sans remplacer le dernier lancement
npm run typecheck
npx shopify store execute --store asia-polene.myshopify.com --query-file <fichier.graphql>   # admin préprod, lecture seule
```

Admin préprod par la CLI Shopify (dans le projet) : connexion `shopify store auth` faite par la QA avec son compte (jeton temporaire, à refaire s'il expire), droits actuels (13 octobre 2026) : produits, stocks, publications, menus et marchés en écriture, emplacements, métaobjets, thèmes, traductions et Roll Out en lecture. La connexion se lance dans un vrai terminal : lancée depuis la conversation (`!`), elle passe en arrière-plan et ne reçoit jamais le retour du navigateur. `--allow-mutations` (toute modification) seulement avec l'accord explicite de la QA, en lui montrant la modification avant.

## Organisation du code

```
playwright.config.ts   Projets = environnement × appareil ("prod · iphone"…), rapports (liste, Playwright, Polène)
src/environments.ts    URL et réglages par environnement
src/fixtures.ts        Neutralisations (cookies, blocage AB Tasty / Klaviyo / pixels), étapes avec capture, diagnostic réseau
src/pages/             Un objet par type de page : header, collection, product, cart, checkout
src/visuel.ts|css      Stabilisation avant capture visuelle (images, vidéos, défilement, carrousels, widgets, barres fixes)
src/shopify.ts         appelShopify : appel direct à la boutique, réessaie sur la limite 429 puis message clair
src/price.ts           Lecture des prix quel que soit le format (640 €, €495,95, $880…)
src/client-test.ts     Charge le client fictif (data/client-test.json + PREPROD_EMAIL)
src/produits-fixes.ts  Charge les produits fixes de la préprod (data/produits-fixes.json : handle, état prévu, tailles…)
src/rapport/           Rapport Polène : reporter.ts (données + historique), types.ts, page/ (index.html, app.css, app.js, logo-polene.svg)
scripts/               ouvrir-rapport (serveur local + sommaire), archiver-rapport, sauvegarder-references
src/accessibilite.ts   axe en cran : analyse (WCAG 2.1 A et AA, textes en français), comparaison au relevé de la page, mise à jour (ACCESSIBILITE_MAJ)
src/controles.ts       Contrôles partagés : erreurs JS à ignorer (pixels, Elevar, mesures Shopify), page pas plus large que l'écran
src/pages/wishlist.ts  Favoris : cœurs des fiches et des cartes, compteur de l'en-tête, rubriques de la page des favoris
tests/                 auth.setup.ts, parcours-achat, structure-collections, collections, recherche, etats-produit, fiche-produit, fiche-galerie, cartes-collection, favoris, panier, checkout, checkout-erreurs, en-tete, pages-sections, compte-client, accessibilite, accessibilite-axe, sante-donnees, demo-echec, visuel, regressions-injectees (.spec.ts)
data/                  client-test, produits-fixes, donnees-qa (produits et collections QA), pages-sections (pages de sections de la préprod et leurs sections attendues, plus les pages réelles qui portent les autres sections)
references/            Captures de référence visuelles : references/<page>/<projet>.png ; relevés d'accessibilité : references/accessibilite/<page>/<projet>.json
```

Résultats : chaque série (`tnr` par défaut, `visuel`, `regressions`, `demo-echec`, déduite de `VISUEL`, `REGRESSIONS`, `DEMO_ECHEC` ou forcée par `SERIE`) range tout dans `resultats/<série>/`, hors Git : `rapport-polene/`, `playwright-report/`, `test-results/` et `historique.json` (40 derniers lancements, pour les graphiques). Rapport Polène (`src/rapport/`) : pièces jointes copiées dans `donnees/`, page statique en JS sans dépendance ; la trace s'ouvre seulement si le rapport est servi par `npm run rapport:polene` (le serveur ne sert que `resultats/` ou l'archive demandée, jamais le projet, et génère le sommaire des séries à la racine). Démos (`@regressions`, `@demo-echec`) : un échec y compte comme « Détecté », sauf s'il vient d'autre chose qu'une vérification (429, délai) : « Non vérifié ».

Charte du rapport, relevée sur polene-paris.com le 6 octobre 2026 (le Figma « Design System » ne contenait qu'une couverture et deux couleurs) :
- **Polices** chargées depuis le CDN du thème (`cdn/shop/t/34/assets/`, ouvert à tous les sites) : Canela Light (`canelaweb-light`, titres) et Sackers (menu de l'en-tête et boutons, sur ordinateur seulement : trop large sur téléphone). Ce sont des polices sous licence : ne pas les copier dans le dépôt. Hors ligne ou si le thème change de numéro (`t/34`), les polices de secours prennent le relais.
- **Lisibilité** (demande QA du 6 octobre 2026, le site pur était trop fin et trop petit) : Canela en Light et non en Thin ; texte courant en Cormorant Garamond de Google, graisse 500 (celle du CDN Polène n'a pas les chiffres alignés, « 2026 » sortait en chiffres bas de casse) ; petites capitales en Jost, 11 à 12 px, légèrement espacées (8 à 10 px en Sackers sur le site). Sur téléphone, textes des graphiques agrandis (le dessin rétrécit avec l'écran). En-tête aligné sur la largeur du contenu (1 232 px).
- **Couleurs** du thème : blanc, beige clair `#F9F8F6`, beige `#EDEAE7`, gris `#757575`, traits `rgba(0,0,0,.1)`, rouge `#D92E50`. Le « vert » du thème est un gris olive : le vert « Réussi » `#0F8060` et l'ocre « Instable » `#C98A14` ont été choisis à côté et vérifiés lisibles par les daltoniens. Un statut est toujours accompagné d'une icône et d'un libellé.
- **Couleurs des graphiques** (hors statuts), tons de cuir vérifiés pour les daltoniens : bleu `#2F5DA8` (toujours le temps : courbe des durées, tests les plus longs, tuile « Durée totale »), cognac `#B0662E` et rose prune `#B86AA8` (raisons d'échec, dans cet ordre, tuile « Commandes créées »). Tuiles surmontées d'un filet de la couleur de leur statut. « Les plus longs » montre la durée habituelle par un trait noir sur chaque barre.
- **Logo** : `logo-polene.svg`, repris du header du site et inséré dans la page par `reporter.ts` (il prend la couleur du texte).
- Formes du site : angles droits, boutons noirs de 40 px, pastilles à contour fin, champ de recherche souligné.

Conventions :
- Chaque étape d'un test passe par `etape(page, testInfo, 'N. Libellé', …)` : nom en français, capture jointe au rapport.
- Localiser par rôle et nom accessible (`getByRole`), avec des expressions qui acceptent FR et EN (la préprod mélange les deux).
- Chemins relatifs à l'URL de base (`'cart'`, `'products/<handle>'`), jamais `'/cart'`, sinon le préfixe `/fr-fr/` saute.
- Comparer les prix en centimes via `parsePriceToCents`. Le prix de référence vient du JSON Shopify `products/<handle>.js`.
- Produits fixes préprod : projet à part `preprod · donnees` (Chrome seul, appareil « Données préprod » dans le rapport), exclu des projets par appareil (`testIgnore`). Un test préprod qui a besoin d'un état précis (rupture, précommande…) prend son produit par `produitFixe('P04')`, jamais un handle écrit en dur.
- Étiquettes : `@smoke` (parcours MEP), `@tnr` (non-régression), `@donnees` (produits fixes), `@accessibilite` (axe et clavier, dans la série tnr), `@demo-echec`, `@visuel` et `@regressions` (exclus par défaut, activés par `DEMO_ECHEC=1`, `VISUEL=1` et `REGRESSIONS=1`). Ne pas créer de test temporaire étiqueté `@visuel` pendant une série : il serait ramassé.
- **Étiquettes de page** (12 octobre 2026, demande QA) : chaque test porte aussi le type de page qu'il vérifie, pour lancer ou filtrer « tout ce qui touche la fiche produit » (`--grep @pdp`, ou recherche « @pdp » dans le Rapport Polène). En anglais, comme chez Polène : `@home`, `@plp` (collection), `@pdp` (fiche produit), `@cart`, `@checkout`, `@search`, `@account`, `@content` (pages éditoriales, Savoir-Faire, boutiques), `@sections` (pages de sections du thème), et `@journey` pour un test qui traverse plusieurs pages (parcours d'achat). Tests visuels : champ `typePage` de `src/visuel.ts` (le dossier des références, `fichier`, garde son nom français). Un test qui vérifie deux pages est découpé en deux tests (ex. rupture : fiche d'un côté, carte de collection de l'autre). Les étiquettes du titre ne comptent pas dans l'historique du rapport (clé sans étiquettes) : on peut en ajouter sans casser les graphiques.
- **Libellé d'un bouton** : lire le texte affiché (`innerText`, avec `expect.poll`), pas `toHaveText` : le bouton principal de la fiche contient les libellés cachés des autres états (« Notify me » est dans le bouton d'un produit en stock).
- Ne jamais reprendre la référence visuelle (`--update-snapshots`) sans l'accord de la QA : c'est son « état validé ». Toujours lancer `npm run test:visuel` avant `test:visuel:maj` et regarder les écarts : la mise à jour remplace les captures différentes sans les montrer. `test:visuel:maj` sauvegarde d'abord toutes les références dans `archives/references/<date-heure>/` (la QA veut garder les anciennes captures) ; pour une seule page, lancer `node scripts/sauvegarder-references.mjs` avant. Vérifier ensuite qu'aucune page mobile n'est plus large que l'écran (une capture iPhone doit faire 393 px de large).
- **Relevés d'accessibilité** (`references/accessibilite/`, 16 octobre 2026) : même règle, `npm run test:accessibilite:maj` seulement avec l'accord de la QA, après un `npm run test:accessibilite` dont on a lu les notes « corrigé ». Il ne fait que retirer ce qui est corrigé ; `ACCESSIBILITE_MAJ=tout` (accepte aussi les nouveaux problèmes) jamais sans accord explicite. Le cran porte sur le type de problème par page, pas sur chaque élément. Une page ajoutée à `data/pages-sections.json` (ou une page prod via `cheminProd`) a besoin de son premier relevé.
- Collections : vérifiées par leur structure (`tests/structure-collections.spec.ts` : cartes, nom, prix, lien, photo, colonnes, PLP breaks), pas en pixels (décision QA du 6 octobre 2026).
- Messages d'assertion en français, compréhensibles par la QA.

## Particularités du site à connaître

- **Bandeau cookies (Consentmo)** : neutralisé par le cookie `cookieconsent_status=allow`, avec un filet de sécurité sur `button[data-csm-button-type="accept"]`.
- **Compteur panier** : texte masqué dans le lien panier du header, « Shopping cart with N items » en prod, « Shopping cart, items: N » en préprod depuis le 12 octobre 2026 (`Header.cartCount` lit les deux).
- **Navigation au clavier** : la fenêtre de géolocalisation de la préprod garde le focus tant qu'elle est ouverte (Tab tourne dedans) : la fermer d'abord. Safari ne passe sur les boutons et liens avec Tab que si l'option du Mac est activée : `Alt+Tab` sous WebKit. L'indicateur de focus du thème est en `:focus-visible` (contour blanc 2 px + halo sombre) : il n'apparaît qu'au clavier, pas après un `focus()` par programme. Le thème défile en douceur jusqu'à l'élément qui reçoit le focus : attendre que la page soit immobile avant de mesurer un défilement.
- **Menu mobile** : toucher une catégorie ouvre un sous-menu, il faut ensuite toucher « Voir tout ».
- **Ajout au panier** : la notification `component-cart-notification.is-active` apparaît. Le bouton de la fiche est `.cta-primary-add-to-cart` (attribut `data-state` : submit, disabled, modal). La notification contient aussi les libellés cachés de la précommande : lire son `innerText`, tout de suite (elle se ferme seule). Sur mobile, le bouton principal est celui de la barre d'achat fixée en bas de l'écran (`.sticky-buy-bar`, cachée une fois le pied de page atteint).
- **Cartes de collection (ajout rapide)** : `.component-product-card`, bouton `.component-quick-add__btn` (« Add to cart » au survol sur ordinateur, icône nommée « <titre> - Add to cart » sur mobile). Bijou à tailles : sur ordinateur, bouton inactif et tailles (« 52 - Add to cart ») à sa place au survol ; le clic de Playwright est refusé pendant la transition (le libellé est encore au-dessus), d'où `CollectionPage.quickAddChooseSize` qui amène la souris et attend que la taille soit au premier plan. Sur mobile, fenêtre « Select size ». Coming soon : `.coming-soon-modal-trigger`, fenêtre `component-modal[data-ref="coming-soon-modal"]`. Étiquette « New in » dans `.component-product-card__tags`. Les fenêtres « Être prévenu(e) » et « Coming soon » refusent un envoi vide ou « test@ » avec « Please type a valid e-mail », sans rien envoyer.
- **Coloris de l'ancienne fiche** : liens `.js-color-option` vers les fiches de la même famille (`filter.families`), `is-active` sur celle affichée ; un clic change de fiche (URL comprise).
- **États produit** : en stock, tailles, tailles partielles, rupture (« Être prévenu(e) »), coming soon (modale, métachamp), précommande (`properties[_is_preorder]`, expire seule après sa date), nouveauté (`LABEL:NEW`). Coming soon et précommande ne sont pas dans le JSON public : sans accès admin, les lire sur les cartes de `collections/all` (`data-tracking-state` : active, disabled, coming-soon, preorder ; 10 pages suffisent) plutôt que fiche par fiche (500 fiches de 450 Ko, plus de 40 min).
- **Deux fiches produit, en préprod et en prod** (même thème), qui alternent parce que l'équipe compare l'ancienne et la nouvelle avec la fonction **Roll Out** de Shopify. En prod, **50/50 depuis le 15 octobre 2026** (annoncé par la QA). Chaque nouveau navigateur peut tomber sur l'une ou l'autre.
  - **Choix de la fiche par les tests** (`src/fiches.ts`, 15 octobre 2026) : Shopify choisit d'après le cookie `_shopify_essential` (même cookie = toujours la même fiche ; le `rolloutTreatmentIds` du HTML change avec). La fixture `fiche` tire des cookies (lecture du HTML de P08, sans ouvrir de page, 2 tirages en moyenne) jusqu'à la fiche voulue et garde le gagnant dans `.auth/fiche-<env>-<fiche>.json` (hors Git). En préprod, ce cookie porte aussi l'accès par mot de passe, ressaisi après chaque tirage. Le panier a son propre cookie (`cart`) : rien de partagé entre tests. `pourChaqueFiche` (`src/fixtures.ts`) déclare un test deux fois (« Ancienne fiche › … », « Nouvelle fiche › … ») : tous les tests `@pdp`. `ficheDeLAppareil` : une fiche par appareil pour les tests qui passent seulement par la fiche (parcours d'achat, panier, favoris du visiteur) : ancienne sur Chrome ordinateur et iPhone, nouvelle sur Safari et Android. Tests visuels : une référence par fiche (`fiche-produit` = nouvelle, `fiche-produit-ancienne` = ancienne, champ `fiche` de `src/visuel.ts`) ; régressions injectées : nouvelle fiche. `ProductPage.goto` vérifie que c'est la bonne fiche. Si le Roll Out ne sert plus une fiche (12 tirages ratés), ses tests se mettent en « ignoré » avec la raison. Favoris du compte : pas de choix (il remplacerait le cookie de la session client).
  - **Nouvelle fiche** : vignettes de coloris dans un carrousel de liens (`a.component-carousel__slide`, `aria-current="page"` sur la fiche affichée, « QA Cyme Mini - Textured Camel, 3 of 3 ») et bouton « Explore all (N) » qui ouvre la fenêtre « Select a color » (onglets All / matières). Tailles : bouton principal « Choose your size » (`data-state="modal"`) qui ouvre une fenêtre, une case radio par taille (« 52 Out of stock », « M Pre-order », `data-state` active, disabled, preorder), bouton d'ajout de la fenêtre (« Please select a size » sans taille, « Notify me » sur une taille épuisée, qui se coche), date de précommande sous les tailles (`.product-add-to-cart__context`), guide des tailles en tableaux (une colonne par unité). Sur téléphone, la fenêtre prend l'écran et reste ouverte après l'ajout. Onglets Description (ouvert au chargement) | Details | Composition | Shipping & Return (rôle `tab`, un seul `tabpanel` affiché). Sur mobile, barre d'achat fixée en bas de l'écran dès l'ouverture : `.product-add-to-cart` en `position: fixed`, avec le bouton seul (ni nom ni prix), toujours visible, pied de page compris ; la page contient une seconde `.product-add-to-cart` vide et cachée, et `product-buy-bar` (nom, prix) reste masquée (`ProductPage.stickyBuyBar` prend la barre visible des deux fiches). Produit dont toutes les tailles sont épuisées (QA11) : « Choose your size », puis « Notify me » dans la fenêtre. Bouton `.cta-primary-add-to-cart` : `data-state` submit (y compris précommande), modal, disabled, coming-soon.
  - **Ancienne fiche** : vignettes de coloris `.js-color-option`, menu « Select size », onglets « Description | Size & fit | Materials | Shipping and returns ». `data-state` active, inactive (taille à choisir), disabled, coming-soon, preorder. **Retouchée en préprod le 15 octobre 2026** : onglets devenus de vrais boutons dans chaque `li` (avant : `li[role=button]`), menu des tailles en `combobox` / `listbox` / `option` avec `aria-disabled="true"` sur une taille épuisée (avant : `disabled="true"`), atteignable et utilisable au clavier (constat 34 corrigé) ; toucher une taille épuisée ouvre « Être prévenu(e) » ; « Notify me » de la fiche ouvre de nouveau la fenêtre (constat 33 corrigé). `ProductPage` accepte les deux balisages. Vue 3D absente aussi en prod sur l'ancienne fiche (constat 43).
  - **Nommage corrigé le 13 octobre 2026 par la QA** : jusque-là, ce dépôt appelait « nouvelle » la fiche à vignettes, apparue en préprod le 7 octobre 2026 vers 10 h 40 (c'est en fait le Roll Out qui a remis l'ancienne pour une partie des navigateurs). Les notes datées d'avant le 13 octobre (ici, dans `docs/reprise-phase-1.md`, `docs/plan-donnees-qa.md`) peuvent encore employer l'ancien nommage.

- Prix des produits QA, 13 octobre 2026 : **le dollar fait référence**, pas de prix fixes en euros.
